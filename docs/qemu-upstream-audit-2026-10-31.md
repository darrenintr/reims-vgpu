# QEMU and Reims vGPU upstream audit — 2026-10-31

This audit is **research only**. It does not update the pinned QEMU binary, the
Stable release, or macOS VM disk images. Do not treat a successful Linux build
as validation of Tahoe on the RX 7600.

## Performance candidates, in order

### A. QEMU memfd / THP (already ported, **not yet benchmarked on RX 7600**)

- Upstream Reims QEMU [`1b41f5f`](https://github.com/steelbrain/qemu-reims-vgpu/commit/1b41f5f5db4d1067d023973b9bd74c7b341e0d28).
- Local backport [`4e9e3de`](https://github.com/darrenintr/qemu-reims-vgpu/commit/4e9e3de2adfe6e333f594811d7bfc4a3a840ac64) in `perf/file-backed-thp-align`; Reims `experiment/qemu-thp` changes its QEMU gitlink.
- Align Linux memfd-backed guest RAM to 2 MiB, allowing shmem transparent huge pages where the kernel policy permits them. An upstream test measured 6–7% less vCPU time per frame on an NVIDIA laptop, **not an RX 7600 result**.
- Check `/sys/kernel/mm/transparent_hugepage/shmem_enabled`, `/proc/<pid>/smaps` or kernel huge-page counters; never change global host huge-page settings without evaluating memory impact. QEMU/KVM dirty logging can force mappings back to 4 KiB on its first harvest, so THP and incremental dirty tracking are not independent additive speedups.

### B. KVM dirty-page tracked, incremental guest-memory copies (**large architectural port**)

- Upstream Reims [`12765ee`](https://github.com/steelbrain/reims-vgpu/commit/12765ee8ae50b6f974b7e544a26acc1771ff703d), 2026-10-28.
- Copy only pages newly written by the guest instead of whole mapped buffer/texture backing every use on discrete GPU paths. Directly relevant in principle to the RX 7600's non-unified memory.
- Requires a new C ABI, KVM dirty-source callbacks in QEMU and corresponding Rust/Vulkan support. Upstream QEMU device code is from a different Reims GPU rail. **Do not cherry-pick just the C or Rust half**.
- Measure copy bytes/frame, dirty harvest time, vCPU exits, frame intervals, correctness and hugepage degradation.

### C. Fewer Vulkan FIFO/task thread handoffs (**performance port**)

- Upstream Reims [`422eab5`](https://github.com/steelbrain/reims-vgpu/commit/422eab5b82ebbb085cbff3dc434384406c0fffc3), 2026-10-28.
- Upstream reports about 0.48–0.9 ms/frame in thread handoffs on one Vulkan host workload, and changed work/reply scheduling to avoid them. RX 7600 must be measured separately.
- Core runtime and task-queue change; preserve ordering, device resets, macOS command completion. Not a QEMU-only feature.

### D. Linux guest-memory mapping budget / dma-buf hardening

- Upstream Reims [`617269d`](https://github.com/steelbrain/reims-vgpu/commit/617269da316ac3d971ff204b6bc4d0b4e68df482) and [`c8e650f`](https://github.com/steelbrain/reims-vgpu/commit/c8e650ff00e116bc0ee6c71869ad7f60faf3d248), 2026-10-28.
- Reduces out-of-VMAs failures at large surfaces/4K by using `/dev/udmabuf`, enforcing `vm.max_map_count` headroom, and detecting missing node/group access. The pinned fork has some earlier mapping-budget code; the later handling is not identical.
- Validate Linux host device permissions, 1080p/4K memory use, no leaked mappings. High reliability value, smaller direct 1080p FPS claim.

## Optional new user-facing features, separate from 120 FPS

- **Video acceleration (experimental):** [VideoToolbox + M2 scaler devices](https://github.com/steelbrain/reims-vgpu/commit/054ac2080e7ba5fe5ea8d19b340f73b329841777) and [VA-API video backend](https://github.com/steelbrain/reims-vgpu/commit/833e496af1dcac4a4f34bc1a15cad7fa63c67bda). Potential RX 7600 video decode on Mesa radeonsi, but needs the matching QEMU devices, kexts, codecs and host driver. Upstream offers a [disable toggle](https://github.com/steelbrain/reims-vgpu/commit/f6b7e92720b886707b3a97f2c695dd066868adae) because the macOS Recovery/install process had compatibility issues. Do not make the default on Tahoe until tested.
- **Post-install NVMe selection:** [Upstream Reims switch](https://github.com/steelbrain/reims-vgpu/commit/e1ab39e7e649ad49ec9568cefc3daa8a09f75378) added optional SATA/NVMe disk-controller setting. **Keep SATA default**: upstream reported macOS 26 installer sometimes could not find a fresh NVMe disk; changing an already installed VM changes OpenCore boot path.
- **USB passthrough management:** QEMU package is already built with libusb and supports `usb-host`; expose a safe `reims-ctl` UI for attaching/detaching host devices after upstream USB lifetime fixes. USB passthrough is not equivalent to a virtual Wi-Fi/AirDrop solution.
- **Built-in performance capture:** the current QMP socket and stats could drive run-scoped frame interval histograms, queue waits and per-stage timing; this may require changes in the Reims library, not QEMU. Present `max gap` is not enough to compute p95/p99.

## Recommended testing sequence

1. Keep Stable [v0.1.1](https://github.com/darrenintr/reims-vgpu/releases/tag/v0.1.1) untouched; compare with the already built Native-v3+Fat-LTO prerelease only in a separate VM run.
2. One QEMU **USB/XHCI/security backport** branch, with compile + QEMU qtests + macOS 26 boot/input/audio/network tests, then A/B. Do not promise FPS improvement from security fixes.
3. One **QEMU THP** branch, retaining exactly the same Rust compiler flags as the current tested baseline; log host THP policy and actual huge-page mapping.
4. One Reims **FIFO/task queue** performance branch; then **dirty-page incremental copy** as a separately gated C ABI/Rust/Vulkan project. Test interaction with THP explicitly.
5. Optional VA-API, NVMe and USB management features, individually opt-in and reversible.

Benchmark an actively animated, matched VM state (Finder window drag 30 s, Safari scrolling 30 s, Launchpad repeat 10x); capture actual per-frame latency if available (median, p95, p99, max), guest/window FPS, CPU pressure, GPU cost estimate, KVM exits and disk/host memory. At 120 FPS, the frame budget is 8.33 ms. Idle periods reporting 0 FPS are not automatically stalls. Keep rollback binary checksum and record the exact running `/proc/<pid>/exe`.

**No tested version is automatically promoted to Stable.**
